# D-29 Agent onboarding: truthful identity, discovery and narrow client setup

**Decided by**: owner (the seven onboarding decisions, all as recommended); the lead with the
platform architecture reviewer (link handling, option b); architecture, security and operations
design review (change 009 design closure) · **Date**: onboarding design, pre-public history ·
**Cited by**: Q-02, C-02, C-10, P4.B-02, P4.I-01, D-25, D-28, change 009

Status: accepted; built by change 009 (phase A, then phase B). Phase B adds the store inspector,
the broad-root rule, doctor, the stdio probe and MCP client setup (below).

## Decision

### Owner decisions (change 009 IDs kept)

| ID | Decision |
|----|----------|
| 009/D-1 | Client setup lives in AGD, narrow: `agd mcp install` writes only project-scope OpenCode or Claude Code files; `agd mcp config` prints everything else |
| 009/D-2 | Client-owned state is never edited by any path; Claude Code local and user setup is a printed, POSIX-quoted `claude mcp add-json` command |
| 009/D-3 | Paths are absolute and verified; machine paths go into a shared project file only with an explicit `--scope project`; no portable mode |
| 009/D-4 | Builds are stamped `bundle` or `source` with a dirty flag and a self-describing label; no build claims a release; `install-local.sh` installs from an isolated cache; no version suffix |
| 009/D-5 | Two executables stay; doctor compares their full producer records |
| 009/D-6 | No skills are written into consumer repositories |
| 009/D-7 | `agd-mcp` refuses broad confinement roots at startup under fixed rules, unless `--allow-broad-root` is given at the launch site; other mount points start; install and config never write the flag |

**Link handling (009/X-1, option b)**: the broad-root decision and the written root use the
canonical path entry point of D-28, and a root with a link component is refused, never resolved.
Users whose project sits behind a link pass the real path. The rejected option (a) was a
decision-only resolver owned by change 008 (more spellings, a second path function).

### Producer identity (`producer` v1)

```json
{ "producerVersion": 1, "name": "agd", "version": "0.3.0", "informationalVersion": "0.3.0+<sha>",
  "sourceRevision": "<sha>", "buildKind": "source", "sourceDirty": false,
  "label": "agd 0.3.0+<sha> (source build)" }
```

- `buildKind` is `bundle` only when built by `scripts/release-bundle.sh` (which CI package smoke
  runs), `source` for every other build; it records the claimed build path, and only a consumer's
  approved pin (package hash and source commit) proves bundle or publication. There is no
  `release` value.
- `sourceDirty` is `true|false|null` (null without Git metadata at build time). `label` is
  `agd <informationalVersion> (<buildKind> build[, dirty|, dirty unknown])`, and guidance tells
  agents to label provenance with exactly it. Kits persist the record (D-25).
- Build properties `AgdBuildKind` (default `source`) and `AgdSourceDirty` are emitted as assembly
  metadata; only the release script passes `bundle`. `--version` text is unchanged. The literal
  `bundle` is asserted only on shipped bytes (every AGD assembly in each package, and the installed
  shims).
- `install-local.sh` isolates only its two tool installs (a private package directory, no cache, a
  config listing only the local feed), removes its temporary directory on every exit path, and
  fails unless both installed `--version` strings equal the freshly built `<version>+<HEAD>` (or
  each other without Git). Its harness runs from a clone and a `git archive` export inside a
  temporary root with redirected home, tool, package and temporary directories, and proves the
  live tree, its ignored files and the real tool directory unchanged.

### Discovery

- **Catalog**: the surface manifest v2 (`manifestVersion: 2`, `tasks[].operations[] {id, cli, mcp,
  summary, keywords, descriptionTerms, recipe}`), embedded once in Core with the agent guide, the
  format reference and the schema. Task groups: `setup`, `documents`, `nodes`, `layout`,
  `geometry`, `style-tokens`, `review`, `export`, `asset-pipeline`, `provided-artifacts`,
  `native-pixels`. Every command and tool is in exactly one operation; every recipe is a guide
  anchor; every description term appears in the tool and command descriptions; planned work is
  never listed (it lives only in the guide's not-yet-available table).
- **Report v2**: `agd capabilities [--task] [--find]` and `get_capabilities(task?, find?)` call one
  I/O-free builder and return equal members apart from `surface` and `workingDirectory`: `report`,
  `reportVersion: 2`, `producer`, `runtime {rid, osArchitecture}`, the D-28 `platform` member
  embedded unchanged, the existing format, domain, limit and resource members, catalog-derived
  `tools`, `tasks` and `filter`. Removing `cliOnly` is this change's declared cutover; replacing
  the old platform fields is change 008's. `find` is ≤ 64 characters, case-insensitive over id,
  summary and keywords; an unknown task or a long `find` is `INVALID_ARGUMENTS`.
- **Server instructions** at `initialize`, byte-equal to the guide section
  `mcp-server-instructions`: call `get_capabilities` with `find` before authoring; read the guide's
  start-here and recipes; label outputs with `producer.label`; report missing capabilities instead
  of writing Python or Node workarounds; and (phase B) run `agd doctor` or call
  `diagnose_environment` on `STORE_CONFLICT`, `PATH_ESCAPE` or `ASSET_PLATFORM_UNSUPPORTED`.
- **Guide**: `docs/agent-guide.md` is canonical, served as `agd://agent-guide` and by
  `agd guide [agent-guide|format|schema] [--section] [--list]`, byte-equal everywhere. Sections
  `start-here`, `mcp-server-instructions`, task recipes, `not-yet-available` (capability, owning
  slice, "until then", always "do not substitute Python or Node; record the gap") and
  `agd-will-not-start` (runtime-not-found and wrong-architecture remedies). A slice that ships a
  capability moves its row into a recipe and adds catalog operations in the same pull request. The
  repository skill becomes a thin pointer with no version or feature claims; user skill folders are
  never touched.
- **Executable recipes**: a `###` section with a `recipe-` anchor, self-contained in an empty
  temporary directory; fixture blocks `json agd-recipe-file path=<relative>`; step blocks
  `sh agd-recipe` whose lines each start with `agd ` (whitespace tokens, simple quoting, a variable
  only as a whole `"$NAME"` token; no pipes, redirects, chaining, globs or other `$`); directives
  `# bind NAME = <JSON Pointer>`, `# expect exit <n>`, `# expect code <CODE>` and
  `# needs <capability>` (a D-28 wire name; where the gate refuses, the harness asserts the next
  step fails with `ASSET_PLATFORM_UNSUPPORTED` instead of skipping). The test suite executes every
  recipe verbatim, also on the installed tools; no shell and no `jq`.
- **Drift guards**: doc-lint over the guide, README and skill fails on an `agd` command or tool
  name absent from the catalog, an unknown error code, a version literal in the skill and (phase B)
  an unregistered doctor check ID; text shipped by a pull request never names a surface that pull
  request does not deliver.

### Store layout inspector

One read-only Core `StoreLayoutInspector` implements the document store's ancestor-marker,
nested-marker and reparse-point rules; the store keeps every call site and order and only
delegates the three check bodies to it (proved by a differential test against a verbatim copy of
the old checks over a generated corpus). Collecting mode reports the first violation exactly as
fail-fast mode would throw, creates nothing, follows no link and is budgeted (100 000 entries,
depth 64 for doctor and install); a truncated scan is never a pass. Classification against the
intended MCP root: a reparse point in a base component or under the root, or another store marker
(including an existing `./.agd` inside the root), fails for MCP document tools; a CLI working
directory inside the root with no CLI store yet only warns.

### Root rule and the broad-root decision

1. Candidate root: `--working-directory`, else the project root (walk up to the nearest `.git`
   directory or file, stopping before a home directory; no `.git` means the working directory).
2. It must exist and be link-free: its canonical form is walked with `lstat`; a link component,
   another `lstat` error or a missing root is `MCP_ROOT_UNSUITABLE` (`link-component`,
   `cannot-verify`, `missing`). The canonical form is what gets written, byte-equal to the server's
   reported `workingDirectory`.
3. For project scope it lies lexically inside the project root (`outside-project`).
4. `BroadRootRule.Decide`, one pure function shared by install, config, doctor and `agd-mcp`
   startup, never throwing: refused for a link component or a walk error, a fixed root (`/`, a
   drive or UNC share root, macOS `/System/Volumes/Data` or `/Volumes/<name>`), or a home directory
   or an ancestor of one, compared by file identity for each present home source (`$HOME`, the
   passwd entry; lexical fallback on errors; `HOME=/` refuses only `/`; with no home known only the
   fixed rules apply). A mount point only warns. Fixed-root and home refusals are
   `CONFINEMENT_ROOT_TOO_BROAD`.
5. The inspector must pass for MCP document tools (`inner-reparse-point`, `store-overlap`,
   `too-large-to-verify`).

**Startup (009/D-7)**: `agd-mcp` applies the decision to its canonical root and exits 2 with a
stderr remedy ("pass --working-directory <project dir>", or a link-free path) unless
`--allow-broad-root`; the decision changes no path, so the confinement root and the reported
`workingDirectory` are identical with and without the flag; `--help` and `--version` work from any
directory. A declared breaking change (home-rooted configurations, linked spellings and containers
whose home is the work directory), stated in the changelog, `agd-mcp --help` and the consumer
handoff note.

### Doctor

`agd doctor` runs checks with stable IDs in a fixed order, each with a status
(`pass|warn|fail|skip|info`), facts and a remedy: `identity.cli` (warn on a source or dirty build),
`identity.mcp` (`MCP_SERVER_NOT_FOUND`, `MCP_SERVER_MISMATCH`), `runtime.dotnet` (fail if not .NET
10, warn on emulation), `platform.support` (from the D-28 probe; never fails, because gates enforce
refusals at the point of use), `render.skia`, `fonts.bundled`, `fonts.system`, `workdir.access`
(the CLI's only write: an exclusively created probe file removed on every exit path),
`store.layout` (the root gate first, then the inspector), `mcp.launch`, `mcp.tools`, `mcp.call`,
`mcp.launch-env`, and `client.opencode.project|user`, `client.claude-code.project|user`.

- The intended MCP root is `--working-directory`, else the project root, never a root taken from
  a client file. A refused root fails `store.layout` with its code, the inspector does not walk it,
  the `mcp.*` and `platform.support` checks skip and no server starts; no remedy ever suggests
  `--allow-broad-root`.
- Client outcomes are static and lexical only (paths and commands from client files are never
  opened, resolved or run): `not-configured`, `matches`, `root-differs` (info, with a doctor
  remedy when the configured root lies inside the project), `differs`, `foreign`, `unresolvable`,
  `unsafe-target`, `oversize`, `unparsable`; an entry with `--allow-broad-root` warns.
- Exit codes: 0 healthy (warnings allowed), 2 any fail, 3 warnings under `--strict`, 4 bad
  arguments, 1 doctor failed, 130 cancelled. Output is deterministic; remedies carry argv only with
  concrete values doctor derived; control and bidi-format characters are stripped from echoed text.
- No network, no store-backed engine, no `./.agd`; the only child processes are the resolved
  server. Server resolution: `--server`, then a sibling of the running `agd`, then an absolute
  `PATH` lookup skipping empty, relative and `.` entries; a hit inside the working directory or
  project is not executed without `--server`. An architecture test keeps `System.Net` out of the
  onboarding code and process spawning out of Core and `agd-mcp`.
- `diagnose_environment` (MCP, read-only, store-free) runs the in-process checks on the server's own
  root, writes nothing (`writable: "untested"`), reports root-relative paths only and redacts echoed
  text with the D-28 redactor.
- Store and platform hints: the CLI appends "run `agd doctor --check store.layout`" to
  `STORE_CONFLICT` and `PATH_ESCAPE` and "`--check platform.support`" to
  `ASSET_PLATFORM_UNSUPPORTED`; MCP appends "call `diagnose_environment`"; codes never change.

### Stdio probe

A hand-written .NET JSON-RPC client shared by doctor and install launches the server in a
client-like environment (`HOME`, `USER`, `LOGNAME`, `TMPDIR`, `LANG`, a minimal system `PATH`,
the entry's `env`; `DOTNET_ROOT` derived from the running runtime, never from an ambient value) and
performs `initialize`, `tools/list` (count equal to the catalog, the shared object-schema rule),
`get_capabilities` (producer equal, `workingDirectory` equal to the canonical root) and
`resources/read agd://agent-guide`. If the scrubbed launch fails it retries with the derived
`DOTNET_ROOT`, then once with the full environment for diagnosis only, naming variables, never
values. Streams are drained concurrently past their bounds; probes time out at 20 s; the whole
process tree is killed and reaped. **An entry is never written unless it passed a probe in exactly
its written form.**

### Client setup

- `agd mcp config --client opencode|claude-code|generic [--scope project|local|user]` prints the
  entry, target and predicted outcome and never writes; byte-identical output for the same inputs.
- `agd mcp install --client opencode|claude-code --scope project` (scope required; `--dry-run`,
  `--force`) applies the root rule, probes, then byte-splices one entry: OpenCode
  `mcp.<name> = {type: local, command, enabled, environment, timeout: 20000}` in an existing
  `opencode.jsonc` or `opencode.json` (both present is unmergeable); Claude Code
  `mcpServers.<name> = {type: stdio, command, args, env}` in `.mcp.json`. It never writes
  `enableAllProjectMcpServers` or approval lists.
- Entry content: the absolute shim path and `--working-directory <canonical root>`; the name matches
  `^[a-z0-9][a-z0-9_-]{0,63}$`; any path or argument with a control character, a bidi-format
  character, `$`, `{` or `}` is refused naming the component (blocks client variable substitution).
- Targets: one shared reader is the only opener of client files; project files that are links,
  FIFOs, devices, foreign-owned, multi-link or outside the project are `unsafe-target` and never
  opened; reads are bounded (1 MiB project, 16 MiB user) and parse errors report positions only; a
  rule the platform cannot verify refuses (`CLIENT_CONFIG_UNSAFE_TARGET`), including a project root
  not owned by the user or world-writable without the sticky bit, and a deny list
  (`~/.claude.json`, `~/.claude/**`, `~/.config/opencode/**`).
- The splice keeps every byte outside the entry span (comments and trailing commas included); a
  deep-equal entry is `unchanged` with no write; a differing entry is `CLIENT_CONFIG_CONFLICT`
  unless `--force`; invalid JSON, duplicate keys, oversize, a bad encoding or both OpenCode files
  are `CLIENT_CONFIG_UNMERGEABLE`; a file changed between read and rename is
  `CLIENT_CONFIG_CHANGED`. The write is a temporary file in the target directory with the target's
  mode, synced, hash re-checked, renamed and re-read; failures leave no temporary file.
- Output shows only the named entry (command, args, root, `env` keys), never other members or
  `env` values. The report's next steps: restart the client, approve the server (Claude Code), run
  `agd doctor --working-directory <written root>`, and check `get_capabilities`.

| Code | Exit | Meaning |
|------|------|---------|
| `INVALID_ARGUMENTS` | 4 | bad client, scope, check, task, `find` or name; refused characters; install without project scope; `--allow-broad-root` passed to install or config |
| `MCP_SERVER_NOT_FOUND`, `MCP_SERVER_MISMATCH`, `MCP_LAUNCH_FAILED`, `MCP_SCHEMA_INCOMPATIBLE` | 1 or a failed check | probe and identity failures |
| `MCP_VERIFY_FAILED` | 1 | the probe failed; nothing written |
| `MCP_ROOT_UNSUITABLE`, `CONFINEMENT_ROOT_TOO_BROAD` | 1, a failed check, or 2 at startup | the root rule |
| `CLIENT_CONFIG_UNSAFE_TARGET`, `_CONFLICT`, `_UNMERGEABLE`, `_CHANGED` | 1 | install target rules |

## Alternatives

- **Documentation only for client setup**: repeats the hours-long setup failure that motivated
  this change. **Writing user or local client config**: edits client-owned state (009/D-2).
- **Portable paths**: machine paths in shared files must be an explicit choice.
- **A version suffix for source builds**: changes the package version across scripts and evidence.
- **One executable**: skew between the two tools is detected instead.
- **Attributes or a source generator for the catalog**: split across assemblies, or cost for one
  file. **A separate recipes resource, MCP prompts or a rich skill**: drift, uneven client support,
  Claude-only and unpackaged.
- **Resolving links in roots** (009/X-1 option a): a second path function and more spellings.

## Revisit when

A client changes its configuration contract; the owner reverses a decision (an answer different
from a recommendation goes through amendment); a release feed or signing makes producer proof
possible without a consumer pin.
